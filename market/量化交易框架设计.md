# Reelax 量化交易框架设计

> 状态：**设计已落地** —— P0~P3 已实装于 `market/`（P4 自动执行为可选）。本文仍是架构、定价模型、风控与执行边界的唯一权威来源，改动前先读。
> 数据来源：`devtools/api.py` 扩展桥（只读）+ 游戏打包 JS 逆向出的接口结构。所有结论基于 2026-08-09 实测数据。

---

## 0. 目标与总体约束

**目标**：自动化发现并执行有利可图的交易，优先级为「以物换物（专精鱼）」>「鱼类市场」>「装备市场（仅低价提醒）」。

**硬性约束**（用户要求）：
1. **低频、串行**：API 请求严禁并发，逐条间隔 2~5s（可配置 + 随机抖动），避免触发会话共享请求频率预算 / 被官方发现。
2. **统一告警**：所有提醒走企业微信 webhook 模块：
3. **执行动作默认人工确认**（见 §5 前置依赖——桥当前只支持 GET，POST 需要先扩展）。

## 1. 三种交易分类与各自模型

### 1.1 以物换物（barter）—— 优先实现

**机制**（实测/逆向确认）：
- 纯鱼换鱼，**无金币、无手续费**。这是它相对其他两个市场的核心优势。
- 方向约定：
  - 订单创建者：`offers` = 交出（给出）的鱼，`requests` = 想要（需求）的鱼。
  - 填充者（我方视角）：给出 `requests` 里的鱼，收到 `offers` 里的鱼。
  - 校验：`offers` 鱼种不重复、与 `requests` 不重叠、**提供鱼总数 ≤ 需求鱼总数**（创建者只能"以小换多"的让利结构）。
- 订单对象字段（`/api/barter/orders` 返回）：
  ```
  { id, ownerNickname, isOwnOrder, status, completionReason, rarity,
    requests: [{ fish: {name, fishId, rarity, biomeId,...}, initialQuantity, remainingQuantity }],
    offers:   [{ fish: {name, fishId, rarity, biomeId,...}, initialQuantity, remainingQuantity }] }
  ```

**接口**：
| 用途 | 方法 | 路径 / 参数 |
|---|---|---|
| 公开订单列表 | GET | `/api/barter/orders?limit=24&canFulfill=true&offersMastery=true&targetFishId=<fishId>&cursor=` |
| 创建订单 | POST | `/api/barter/orders` body=`{requests:[{fishId,quantity}], offers:[{fishId,quantity}]}` |
| 填充订单 | POST | `/api/barter/orders/{id}/fill` body=`{orderId, requestFishId, offerFishId}` |
| 我的挂单 | GET | `/api/barter/me/orders?limit=24&status=active` |
| 我的成交 | GET | `/api/barter/me/trades?limit=30` |

- 筛选参数语义（页面按钮对应）：
  - `canFulfill=true` →「我能填的单」：我的库存能给出 `requests` 的订单。
  - `offersMastery=true` →「提供鱼中有专精目标」：`offers` 里含专精鱼。
  - `targetFishId=<id>` → 指定某个鱼在 `offers` 中（定位特定专精鱼来源）。
- 所有 POST 需带 `Idempotency-Key` 头（uuid），重试时**复用同一 key**（游戏端逻辑：payload 签名相同则复用 idempotencyKey，见 bundle 的 `H0()`）。

**策略核心（专精鱼导向）**：
1. `GET /api/mastery` → 每个 biome 有 9 档稀有度的「专精鱼」链（common→uncommon→fine→rare→epic→legendary→mythic→exotic→arcane），字段 `contributedQuantity / requiredQuantity`、`isFishLocked`、`availableQuantity`。
2. 找出所有 `contributed < required` 且未锁定/已解锁的专精鱼，作为「需求集」。
3. 对每个目标专精鱼 `f`：`GET /api/barter/orders?canFulfill=true&offersMastery=true&targetFishId=f`。
4. 逐单判定「我能填吗」：**填单是单对单部分填** —— 一次 fill 只给出 `requests` 里的 1 条鱼、换回 `offers` 里的 1 条鱼，不需要凑齐 `requests` 全部鱼。
   所以只需存在**任意一组**可行配对即可，判定条件（`/api/inventory/fish`）：
   `quantity > BARTER_KEEP_MIN` 且 `isLocked == false`（手动锁与专精锁的鱼都交易不出去）。
5. 用 §3 的评分模型打分，超过阈值 → webhook 提醒 /（可选）自动填单。

### 1.2 鱼类市场（fish market）—— 次优先

**机制**（实测确认）：
- **卖方税 5%**：`market-config.sellerFeeBasisPoints = 500`。成交 `gross = quantity × unitPrice`，`fee = gross × 5%`，`sellerProceeds = gross - fee`。
- 挂单上限 50 单，单鱼最大 100,000 条，挂单 7 天（604800s）。

**接口**：
| 用途 | 路径 |
|---|---|
| 行情总览 | GET `/api/market/fish/overview` → `fish:[{fishId, latestTradeUnitPrice, priceChange24hBasisPoints, sellOrderQuantity, buyOrderQuantity}]` |
| 订单查询 | GET `/api/market/orders?assetType=fish&side=&limit=` |
| 我的挂单/成交 | GET `/api/market/me/orders`、`/api/market/me/trades` |

**我的实测成交画像**（设计依据，2026-08-08~09）：
- 30 条成交，seller 15 / buyer 15；鱼种集中在 legendary（单价 1.4w~2.2w）与 mythic（如 命轮月鳗 14w）。
- 确认手续费 5%（例：gross 40000 → fee 2000 → proceeds 38000）。

**策略核心**：
- 定价参考 = `fish/overview.latestTradeUnitPrice`（有 510/529 种鱼有最新成交价）+ 库存 `sellPrice`（NPC 保底价）。
- 卖出决策：挂单净得 = 挂单价 × 0.95；若低于 NPC 保底价则直接 NPC 卖，不挂单。
- 套利方向：买入低价挂单 → 高价挂出，**净收益 = 卖出价×0.95 − 买入价**，必须覆盖价差成本（税后模型，见 §3）。
- 提醒：overview 中 `priceChange24hBasisPoints` 波动大 / 深度（sellOrderQuantity）异常的鱼。

### 1.3 装备市场（gear market）—— 只做低价提醒

**机制**：装备挂单同样 `feeBasisPoints=500`；装备有 `rarity / slot / stat / quality(0-100) / minUpgradeLevel` 多维度，定价复杂。

**接口**：
- `GET /api/market/orders?assetType=gear&side=sell&rarities=legendary,mythic&maxPrice=...&slot=&stat=&minQuality=&minUpgradeLevel=`
- 参数名映射（页面筛选名 → API 名）：`gearRarities→rarities`、`gearMaxPrice→maxPrice`、`gearMinPrice→minPrice`、`gearSlot→slot`、`gearStat→stat`、`gearMinQuality→minQuality`、`gearMinUpgrade→minUpgradeLevel`。

**本期只做**：定期（如每 30~60 分钟，低频）扫 legendary/mythic 低价挂单，与参考价（历史成交中位数/同词条均值）比较，明显低估 → webhook 提醒。**不自动买入、不参与估价模型**，留待二期。

## 3. 定价与评分模型（量化核心）

### 3.1 鱼的统一价值
```
value(fish) = max(市场参考价, NPC保底价) × (1 + 专精加成)
```
- 市场参考价：`fish/overview.latestTradeUnitPrice`（缺省用库存 `sellPrice`）。
- NPC 保底：`inventory/fish.sellPrice`（卖 NPC 即时到手，无税）。
- **专精加成**：若 `fish` 是未完成专精目标 → 其价值不只市场价格，还含「完成 tier 的边际收益」：
  - tier 完成收益：该 biome 的 `xpBonusBasisPoints` / `directGoldBonusBasisPoints`（`/api/mastery` 的 biome 字段），以及解锁下一稀有度档位的长期价值。
  - 简化折算：`专精溢价 = baseValue / remainingQuantity`（把完成进度所需的最后几条鱼定价更高，即"最后一公里溢价"）。具体系数留作策略参数调优。

### 3.2 barter 交易评分
```
评分 = Σ 收到鱼价值(含专精加成) − Σ 给出鱼价值(机会成本)
机会成本 = 给出鱼若挂市场卖的税后净得（≈ 市场价 × 0.95，因为 barter 无税，实际更划算）
```
- 若 `评分 > 阈值` → 报单提醒。
- 附加判断：给出鱼必须是我库存**过剩**的（`quantity` 远大于保留量），避免清空刚需鱼。
- 空手限制：barter 不能凭空创造价值，评分必须>0 才值得做；专精溢价是主要正分来源。

### 3.3 鱼类市场税后模型
```
卖出净得(P)  = 挂单价 × (1 − 0.05)          # 挂单卖出
NPC净得(N)   = sellPrice                    # 秒卖 NPC
套利净利     = P(卖) − 买价                   # 买入→卖出，两侧都要过税
```
- 挂单决策：`P > N` 才挂单；否则 NPC 卖。
- 套利决策：`P(卖) − 买价 > 手续费损耗 + 阈值` 才执行，且要评估 7 天挂单期的流动性（参考 overview 的买卖深度）。

### 3.4 装备低价（仅提醒）
```
低估程度 = 1 − 挂单价 / 参考价
参考价   = 同 rarity+slot(+stat) 的历史成交中位数（从 /api/market/me/trades 及其他来源积累）
低于阈值（如 < 60%）→ webhook 提醒
```

## 4. 风控与隐蔽性（核心要求）

1. **串行调度**：`main.py` 单线程；每个 API 调用后 `sleep(base + random(0, jitter))`，默认 base=2.5s、jitter=2s。绝不并行。
2. **不粗暴轮询**：能复用游戏内置 `window.arcaneReelax` 快照（`/api/mastery` 等有快照的优先用快照）就走快照；走桥的只读查询保持低 QPS。
3. **会话共享频率预算**：官方文档明确登录后 API 按会话共享总频率预算，脚本要避免影响正常游戏——策略轮询周期以分钟计，不用秒级轮询。
4. **单类市场单次运行**：三个模块不在同一时刻叠加跑（调度器错峰）。
5. **幂等与重试**：POST 全部带 `Idempotency-Key`；403 签名失效自动重置 proof 重试一次（复用 sign.js/bridge.js 既有逻辑）。
6. **执行默认人工确认**：策略只产出「候选单」，通过 webhook 推给用户，用户确认后（或配置自动模式）才发 POST。

## 5. 执行层前置依赖（未实装，需先做）

**关键缺口**：`bridge.js` 目前只有 `bridgeSignedGet`（GET），而 barter 填充/创建、市场挂单都是 **POST**。

待实现选项（任选其一）：
1. **扩展桥加 POST**（已实装）：`bridge.js` 新增通用 `bridgeSignedRequest(method, path, body, idempotencyKey)`（body 参与签名 + `Idempotency-Key` 头）；`api.py` 的 `Bridge.submit` 支持 method/body 下发，任务结构为 `{id, path, method, body}`。
2. **RDP + sign.js 通道**：`sign.js` 的 `signedFetch` 已支持 method/body，可经 RDP 注入后执行 POST。缺点：RDP 依赖调试端口、不如桥稳定。

**验证清单（POST 已实装，待真机联测）**：
- `POST /api/barter/orders` 创建成功 → `GET /api/barter/me/orders` 可见。
- `POST /api/barter/orders/{id}/fill` 填单成功 → `GET /api/barter/me/trades` 有记录。
- 幂等：同 payload 重复 POST 不产生重复订单。

## 6. 企业微信 webhook 告警模块（alerts.py）

- 统一入口：`send_alert(kind, title, content)` → `POST {webhook}` body=`{"msgtype":"markdown","markdown":{"content":...}}`（或 text）。
- 事件种类：`deal_found`（barter 好单）、`price_drop`（鱼/装备低价）、`execution_success`、`execution_fail`、`error`、`daily_summary`。
- **节流**：同类告警 N 分钟（默认 30）内最多一条；订单去重（store.py 记 orderId）。
- 失败重试：webhook 返回非 0 错误码时退避重试 1~2 次，仍失败记本地日志。

## 7. 数据落盘（store.py）

- **订单去重**：`seen_orders(orderId, kind)` —— 已提醒过的订单不重复提醒。
- **价格历史**：`fish_prices(fishId, ts, price, source)` —— 支撑参考价中位数/移动平均。
- **成交记录**：拉取 `/api/market/me/trades` 与 `/api/barter/me/trades` 增量入库，作为历史画像与参考价来源。
- 存储用 SQLite 单文件（标准库 sqlite3），避免引入第三方依赖。

## 9. 风险清单

- **误判风险**：overview 的 `latestTradeUnitPrice` 是最近一笔成交价，可能失真；参考价需要多日数据平滑。
- **流动性风险**：barter 好单可能被秒填（每次轮询间隔内被抢）；高价值鱼挂单 7 天可能卖不出。
- **被发现风险**：低频串行 + 快照优先是底线；POST 执行动作比只读更敏感，默认人工确认。
- **专精锁定**：`isFishLocked` 表示前一档未完成，需求集要过滤 locked 鱼，避免换回来也交不了。
